# Resume editor

A private, single-operator editor for named resumes, each with one freely editable Markdown document. This module owns editing, document actions, transient import drafts, and source/PDF exports. Database declarations remain in `db/schema.ts`; the existing postgres-js/Drizzle client owns connections. There is no account, ownership, public-service access control, AI service, or separate backend. Run only on a trusted private machine/network; bind local services to loopback. Robots directives and no-store responses are privacy hygiene, not authentication.

## Source and persistence

One `resumes` row owns a document's plain-text name, UUID, `contentMarkdown` text, Classic theme key, positive integer version, and timezone-aware timestamps. The entire source string is authoritative, including headings, fences and whitespace. No section identities, separate title fields or fixed employment/education schema exist. HTML, PDFs and uploaded files are never document source.

Actions bound names to 120 UTF-16 units and Markdown to 500,000 units. The Server Action transport budget is 4 MiB to accommodate worst-case JSON escaping at that source bound; upload bounds remain separate. Empty documents are valid. Source must be well-formed Unicode without null characters so PostgreSQL text and UTF-8 exports cannot silently replace unsupported code units. Update and delete compare the acknowledged version in the same SQL statement that changes the row. A stale/deleted row fails rather than silently overwriting another tab.

The initial Drizzle migration targets a fresh database, as requested. There is no legacy section-schema migration, backfill, compatibility mode or automatic database/volume reset.

Database access initializes through the shared `getDb()` accessor on first use, not module import. Route configuration collection and builds therefore require neither `DATABASE_URL` nor a running database. Missing configuration still fails clearly when storage is used. The Drizzle instance is cached per module; development reloads reuse the connection pool without introducing global pool caching in production.

The client debounces edits, serializes writes, and coalesces changes made during an in-flight request. It advances versions only after acknowledgement and never labels newer pending text as saved. Switching, creating, deleting, renaming, and exporting flush the queue before proceeding; transition/export controls lock input until the operation finishes. Failure retains the open document and local edits, blocks automatic retries, and exposes explicit retry plus an unsaved Markdown backup. Leaving with dirty content triggers the browser's unload warning. There is no persistent browser copy of personal documents. The selected UUID travels in the URL so reload restores the selected document without storing its content client-side.

## Markdown and import drafts

Markdown imports decode UTF-8 strictly and keep the entire source without heading splitting or reconstruction. Unedited imports preserve BOM, CRLF, trailing whitespace, fences and heading delimiters through review, persistence and export. Markdown export and unsaved backups return the source directly, without synthesized headings or application metadata. Editing uses a normal textarea, including browser newline normalization when the source is changed. Reference-link definitions resolve throughout the source in both Classic renderers; the first definition wins.

Import handlers bound multipart input and return reviewable drafts, not database writes. Only confirmation creates a new resume; no import overwrites an existing document. UTF-8 Markdown is limited by document bounds. PDF uploads are at most 10 MiB and 20 pages. Local unpdf/PDF.js extraction rejects invalid, encrypted (including empty-user-password encryption), and entirely textless PDFs, and warns about pages without recovered text. Extracted text is conservatively escaped into a whole-document Markdown draft. Single extracted line separators become explicit Markdown hard breaks so preview and PDF re-export retain visible line boundaries; existing paragraph/page separators remain blank lines. This conversion applies only to new PDF imports, not normal Markdown soft breaks or existing saved source. Conversion does not infer section structure, perform OCR or reconstruct layout; it makes no external calls and does not promise reading-order fidelity. Original bytes remain transient. These bounds are not public-upload sandboxing.

## Classic Markdown preview and PDF export

One browser-safe, allowlisted Markdown traversal produces the shared document tree for separate React HTML and Node-only React PDF adapters. One Classic theme defines typography, spacing and print colors; both adapters use the same bundled OFL-licensed Lato regular/bold/italic/bold-italic faces. The browser receives local fonts through Next's static font assets; PDF export embeds the original faces. Headings, paragraphs, emphasis, bold, lists, links, quotes, rules and code are supported. Unsupported Markdown remains visible as literal source with shared warnings; unsupported task items must not acquire a second list marker or lose subsequent ordered numbering. Raw HTML is never injected or executed, and Markdown cannot select image/font/resource fetches. Only validated HTTP(S) and mailto destinations become links; browser links open a separate tab without an opener or referrer.

Classic uses compact resume typography inspired by `junian/markdown-resume`: a centered, letter-spaced H1 name, smaller left-aligned H2–H6 headings, thin full-container-width bottom rules on every heading, and tighter body/paragraph/list spacing with shallow bullet indents. All H1 headings receive the same treatment, including after preambles or within nested content; no title/contact fields are inferred or synthesized. Both adapters take these values from the shared theme while retaining Lato, the existing print palette and Letter geometry. The shared list inset expands for additional ordered-marker digits so compact lists cannot put numbers over body text. This borrows the reference's visual hierarchy without importing its raw-HTML injection, custom CSS, definition-list layout or external-resource behavior. HTML remains unsupported; [the research note](../../docs/research/resume-html-support.md) describes a possible future extension, not an accepted input contract.

The right pane renders current local Markdown, including unsaved or failed-save edits, without document/PDF network requests or PDF generation. Parsing and rendering failures are contained inside that pane: they show a generic preview error without unmounting editing/autosave or losing Markdown download/recovery controls. Changing the source retries the preview. Extremely nested source can exceed parser/layout limits even within document-size bounds; saving and Markdown recovery remain independent of preview/PDF success. Before mounting HTML, an iterative check limits the preview tree to 16 nested Markdown levels, including inline content and list-item containers. This conservative browser-only safety budget prevents renderer-process crashes that an exception boundary cannot catch; it never changes source, persistence validation or PDF export policy. It is a continuous reading preview, not a paginated PDF proof. HTML and PDF share content and Classic styling, but line breaks, responsive preview margins and pagination can differ because they use different layout engines. The exported PDF is the final print layout. This intentional trade-off avoids costly background PDF rendering while editing; there is no hidden iframe, saved-version preview queue, preview blob URL or manual PDF-refresh control.

Only explicit PDF export calls the Node renderer against a requested saved version. Export flushes edits first and handlers reject version mismatches. Normal PDF body words stay intact; long identifiers can wrap by grapheme chunks rather than clipping or shrinking the document. Body tokens up to 24 graphemes stay whole, while headings offer 12-grapheme breaks sooner because the larger tracked H1 can overflow at the body threshold. Both callbacks bind their limits explicitly rather than accepting React PDF's auxiliary callback argument as a limit. Neither policy splits graphemes or shrinks the chosen typography. Longer content naturally paginates on Letter paper with selectable text. Lato's glyph coverage is not universal. PDF generation/extraction and database code remain server-only; only safe parsing, Classic style data and HTML preview code enter the browser. Document responses use private/no-store headers. Next automatic logging is disabled because development Server Function tracing otherwise serializes document arguments and request logs expose document identifiers. Errors remain generic and do not log resume source. PDF fonts are included in Next output tracing; no browser binary is required on the server.

## Presentation boundary

The left pane has one labeled Markdown textarea; headings are ordinary source, not separately managed fields. Import review likewise has one editable draft plus its document name. This replaces section editing rather than adding a second mode or rich-editor toolbar. The current document name opens a transient dropdown containing choices, New, and Import. Rename/Delete live in the current document's overflow menu; export actions remain on the right. There is no persistent document list/sidebar, drag-and-drop framework, theme gallery, or live job/profile/AI navigation.

Canonical Kyu semantic tokens style a centered editor-specific 80rem/1280px frame **including** 30px gutters (22px at 650px and below). The navbar contents, navbar bottom rule, document title/actions and both equal-width panes share this frame. This is the user-approved exception to the original default 55rem frame: wider editing and preview space must not become a full-width dashboard or persistent sidebar. The two panes use all interior width, shrink with available space and stack on narrow screens. Mantine's stylesheet/provider and root font size remain intact. The root color-scheme script and provider both default to `auto`, resolving the system preference before hydration and following preference changes while open. Scoped Kyu semantic tokens use that resolved scheme for the canvas, controls and portaled menus/dialogs. Dark mode uses the user-selected black canvas, neutral charcoal controls and gray actions/links/focus rather than the original green-tinted palette; semantic warning/error colors remain distinguishable. Light-mode colors are unchanged. Classic preview paper and exported colors remain independent of the UI scheme and stay white with print ink. Routine UI copy is minimal; save status, validation, destructive-action and recovery feedback remain explicit. Native semantics, focus restoration, visible focus, coarse-pointer 44px targets, reduced motion, zoom, and a 320px no-page-overflow layout govern the editor and its overlays.

## Verification boundaries

Unit tests cover coalescing, acknowledged versions, transport failures, failed-switch preservation, immediate local Markdown rendering, shared styles, semantic/safe HTML and preview-failure containment/recovery. Shared-parser tests prove references, entity/escape behavior, literal unsupported source and URL safety once for both adapters. Generated PDF fixtures verify actual text, four embedded fonts, page geometry/flow, links, matching warnings and extraction errors. The database integration runner creates a new ephemeral loopback PostgreSQL container, waits for TCP readiness rather than PostgreSQL's temporary bootstrap socket, applies committed migrations, proves exact whole-source CRUD and competing-version writes, and removes only that container. CI builds with an explicitly empty `DATABASE_URL`, runs unit/document tests without a database, then invokes this isolated runner; it uses no operator database credentials or persistent test service. Browser tests exercise actual server actions, one freely editable source with no section controls, exact BOM/CRLF import/export, full-bound worst-case JSON transport, two-tab conflicts, document selection/reload, desktop/intermediate/narrow keyboard/touch/text-scaling behavior and OS scheme changes before/after hydration, including open portals. Network assertions prove no PDF requests during editing or document switches and exactly one on explicit PDF export; extracted download text proves pending edits were flushed. Computed browser contrast checks cover dark input text/placeholders, borders, focus and primary actions. A deeply nested within-limit fixture proves preview failure cannot cancel saving, prevent reopening saved source, remove unsaved Markdown backups or stop recovery after editing. The HTML preview remains usable without browser PDF embedding. User-owned databases and environment files are never reset for verification.
